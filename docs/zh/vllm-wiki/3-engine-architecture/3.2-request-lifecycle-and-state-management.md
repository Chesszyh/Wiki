本文档描述了请求如何在 vLLM 的 V1 引擎中流转、它们会经历哪些状态迁移，以及其进度如何被跟踪。它涵盖了从创建到完成的 `Request` 对象生命周期、由调度器管理的状态转换，以及用于跟踪请求进度和输出的机制。

## 目的与范围

本页文档涵盖：

-   `Request` 类及其在跟踪请求状态中的作用。
-   请求状态及状态迁移逻辑。
-   从提交到完成的请求生命周期。
-   调度器如何管理请求队列和状态。
-   请求元数据跟踪（已计算 token、已生成输出等）。
-   特殊请求状态（抢占、流式处理、远程 KV 加载）。

## 调度器状态管理

### 请求队列

`Scheduler` 管理三类主要请求集合：

1.  **`self.requests`**：将 `request_id` 映射到 `Request` 对象的字典，包含所有活动请求 [vllm/v1/core/sched/scheduler.py157](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L157-L157)
2.  **`self.waiting`**：包含等待调度请求的 `RequestQueue` [vllm/v1/core/sched/scheduler.py166](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L166-L166)
3.  **`self.running`**：当前正在处理的请求列表 [vllm/v1/core/sched/scheduler.py168](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L168-L168)

### 调度周期（`schedule()`）

`schedule()` 函数是状态管理的核心：

-   它根据 `SchedulingPolicy`（例如 FCFS）尝试从 `waiting` 队列中调度新请求。 [vllm/v1/core/sched/scheduler.py160](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L160-L160)
-   它检查 `max_num_running_reqs` 和 `max_num_scheduled_tokens` 等资源约束。 [vllm/v1/core/sched/scheduler.py105-110](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L105-L110)
-   对于每个请求，它会与 `KVCacheManager` 交互以分配块。 [vllm/v1/core/kv\_cache\_manager.py106](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/kv_cache_manager.py#L106-L106)

**来源：** [vllm/v1/core/sched/scheduler.py322-897](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L322-L897) [vllm/v1/core/kv\_cache\_manager.py106-145](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/kv_cache_manager.py#L106-L145)

### 输出处理与完成（`update_from_output()`）

在 `GPUModelRunner` 执行之后，调度器会更新请求状态：

-   **Token 更新**：增加 `num_computed_tokens` 并追加新的 `sampled_token_ids`。 [vllm/v1/core/sched/scheduler.py900-950](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L900-L950)
-   **停止条件**：调用 `check_stop()` 评估 EOS token、停止字符串或最大长度。 [vllm/v1/core/sched/utils.py53](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/utils.py#L53-L53)
-   **已完成请求**：如果请求完成，它会从 `self.requests` 中移除，并通过 `finish_requests()` 释放其 KV 块。 [vllm/v1/core/sched/scheduler.py294-320](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L294-L320)

**来源：** [vllm/v1/core/sched/scheduler.py899-1204](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L899-L1204)

## 结构化输出状态

对于需要结构化输出（例如 JSON）的请求，状态管理涉及 `StructuredOutputManager`。

1.  **初始化**：在请求被添加时调用 `grammar_init(request)`。 [vllm/v1/structured\_output/__init__.py97](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/__init__.py#L97-L97)
2.  **编译**：管理器使用某个后端（如 `XgrammarBackend`）将 schema 编译为 `StructuredOutputGrammar`。 [vllm/v1/structured\_output/__init__.py117-147](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/__init__.py#L117-L147)
3.  **执行**：在采样期间，语法通过 `accept_tokens()` 推进，以约束下一次 token 选择。 [vllm/v1/structured\_output/backend\_xgrammar.py148](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/backend_xgrammar.py#L148-L148)

**来源：** [vllm/v1/structured\_output/__init__.py35-165](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/__init__.py#L35-L165) [vllm/v1/structured\_output/backend\_xgrammar.py132-188](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/backend_xgrammar.py#L132-L188)
