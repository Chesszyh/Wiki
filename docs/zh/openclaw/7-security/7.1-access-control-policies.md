本页介绍了 OpenClaw 的访问控制策略 (Access Control Policies)，这些策略决定了谁可以与网关和通道交互。该系统采用“默认拒绝” (deny-by-default) 架构，通过三层过滤强制执行：网关身份验证、通道级策略和命令授权。

有关通用的安全架构概览，请参见 [7](/openclaw/openclaw/7-security)。有关 Docker 沙箱隔离，请参见 [7.2](/openclaw/openclaw/7.2-sandboxing)。

## 策略层级概览 (Policy Layers Overview)

入站请求必须通过三个独立的验证门限才能被分发到智能体运行时。

| 层级 | 强制执行点 | 目的 |
| --- | --- | --- |
| **1. 网关身份验证** | WebSocket 握手 / HTTP 标头 | 验证客户端是否有权访问网关 API。 |
| **2. 通道访问策略** | `monitor` (监听器) / `dispatch` (分发) | 根据发送者 ID 或群组成员身份过滤消息。 |
| **3. 命令授权** | 命令处理器 | 限制哪些发送者可以执行敏感的斜杠命令。 |

---

## 第一层：网关身份验证 (Gateway Authentication)

网关在其 WebSocket 和 HTTP 端口强制执行身份验证。

### 身份验证模式 (`gateway.auth.mode`)

-   `token`：客户端必须在 `Authorization: Bearer <token>` 标头或 WebSocket 连接参数中提供共享密钥。
-   `password`：允许基于用户名和密码的登录（通常用于控制 UI）。
-   `none`：完全禁用身份验证（仅推荐用于受防火墙保护的本地回环开发）。

### 基于角色的访问 (Role-Based Access)

成功通过身份验证的客户端会被分配一个 **角色 (Role)**，该角色决定了它们可以调用的 RPC 方法。

-   `operator`：完全访问权限（配置、会话管理、智能体文件）。
-   `node`：仅限节点特定的方法（能力通告、动作结果）。
-   `user`：受限访问权限（仅限聊天和会话历史）。

**来源**：[src/gateway/server-methods/connect.ts](https://github.com/openclaw/openclaw/blob/8873e13f/src/gateway/server-methods/connect.ts) [docs/gateway/configuration.md420-450](https://github.com/openclaw/openclaw/blob/8873e13f/docs/gateway/configuration.md#L420-L450)

## 第二层：通道访问策略 (Channel Access Policies)

通道级策略在 `openclaw.json` 中配置，控制外部消息（Telegram、WhatsApp 等）如何进入系统。

### 私信策略 (`dmPolicy`)

| 模式 | 行为 |
| --- | --- |
| `pairing` (默认) | 未知发送者必须通过一次性代码挑战。已批准的发送者存储在本地。 |
| `allowlist` | 仅接受显式列在 `allowFrom` 中的发送者 ID。 |
| `open` | 接受所有私信（需设置 `allowFrom: ["*"]`）。 |
| `disabled` | 忽略所有私信。 |

### 群组策略 (`groupPolicy`)

-   `allowlist` (默认)：仅响应已显式配置的群组/服务器。
-   `open`：响应任何包含机器人的群组。
-   `disabled`：忽略所有群组消息。

### 提及门控 (`requireMention`)

在群组中，即使该群组在白名单内，也可以要求显式提到机器人（通过 `@提及` 或正则表达式模式）才触发智能体回复。

**来源**：[src/security/dm-policy-shared.js](https://github.com/openclaw/openclaw/blob/8873e13f/src/security/dm-policy-shared.js) [src/config/zod-schema.core.ts20-34](https://github.com/openclaw/openclaw/blob/8873e13f/src/config/zod-schema.core.ts#L20-L34)

## 第三层：命令授权 (Command Authorization)

命令授权控制谁可以在聊天界面执行 `/status`、`/reset` 或 `/config` 等操作。

### 优先级顺序

1.  **`commands.allowFrom`**：若设置，则它是**唯一**的来源。它会覆盖所有通道级白名单。
2.  **通道白名单 + 配对**：若未设置 `commands.allowFrom`，则继承通道的授权状态。
3.  **`commands.useAccessGroups`** (默认 `true`)：确保遵守群组特定的策略限制。

### 敏感命令门控

某些命令 (`bash`、`config`、`debug`) 具有额外的配置开关。即使发送者已获授权，如果 `commands.config` 未设为 `true`，`/config` 命令仍将被拒绝。
