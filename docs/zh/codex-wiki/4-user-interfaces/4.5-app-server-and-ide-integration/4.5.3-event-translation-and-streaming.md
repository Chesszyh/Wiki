## 目的与范围

本页记录 **BespokeEventHandler** 系统：它将核心 codex 事件转换为发送给连接到 app server 的 IDE 客户端的 JSON-RPC 通知。当线程执行时（运行模型推理、执行工具、应用补丁），核心会发出 `EventMsg` 变体流。app server 必须将其转换为符合协议 schema 的面向客户端 `ServerNotification` 消息。

关于请求处理与线程/回合管理 API，请参见 [Thread and Turn Management API (4.5.2)](https://github.com/openai/codex/blob/d807d44a/Thread and Turn Management API (4.5.2))。关于 app server 的整体架构，请参见 [CodexMessageProcessor and Request Handling (4.5.1)](https://github.com/openai/codex/blob/d807d44a/CodexMessageProcessor and Request Handling (4.5.1))

## API 版本处理

转换层同时支持 V1（遗留）与 V2 API。[codex-rs/app-server/src/codex\_message\_processor.rs388-393](https://github.com/openai/codex/blob/d807d44a/codex-rs/app-server/src/codex_message_processor.rs#L388-L393) 中定义的 `ApiVersion` 枚举控制使用哪套协议结构。默认值为 `V2`。

| `ApiVersion` | Item 生命周期 | 审批模式 | 示例类型 |
| --- | --- | --- | --- |
| `V1` | 隐式（遗留） | 直接向客户端发送审批参数 | `ApplyPatchApprovalParams`, `ExecCommandApprovalParams` |
| `V2` | 显式（`ItemStarted` / delta / `ItemCompleted`） | 以 `item_id` 为作用域的请求/响应 | `ItemStartedNotification`, `FileChangeRequestApprovalParams` |

**V1 与 V2 转换示例 - 文件变更**

```mermaid
flowchart TD
    CoreEvent["ApplyPatchApprovalRequestEvent{call_id, changes, reason}"]
    V1Approval["ApplyPatchApprovalParams{conversation_id, call_id, file_changes}"]
    V1Flow["Direct approval requestNo item lifecycle"]
    V2Started["ItemStartedNotification{item: FileChange, status: InProgress}"]
    V2Approval["FileChangeRequestApprovalParams{thread_id, item_id, reason}"]
    V2Completed["ItemCompletedNotification{item: FileChange, status: Applied/Failed}"]

    CoreEvent --> V1Approval
    CoreEvent --> V2Started
    V2Started --> V2Approval
    V2Approval --> V2Completed
```

## 流式架构

事件通过多层架构从核心线程流向客户端。

**流式架构组件**

```mermaid
    ThreadScoped --> ConnectionIds
    ThreadScoped --> Router
    Router --> OutboundState
    OutboundState --> Writers
    Writers --> StdioWriter
    Writers --> WsWriter
```
**背压处理**

所有通道都是有界的。若客户端消费通知较慢：

1.  出站队列会被填满
2.  通道上的 `send()` 会阻塞
3.  事件监听任务会暂停
4.  核心继续生成事件（内部缓冲）
5.  客户端追上后，事件恢复发送

## 通知退订（Opt-Out）

客户端可在初始化期间退订特定通知，以减少带宽占用或仅处理某些事件。

**退订机制**

```mermaid
flowchart TD
    Init["InitializeParamscapabilities.optOutNotificationMethods"]
    Storage["ConnectionSessionStateopted_out_notification_methods: HashSet"]
    Check["route_outgoing_envelope()Filter by method name"]
    Drop["Drop notificationif method in opted_out set"]
    Send["Write to connectionif not opted out"]

    Init --> Storage
    Storage --> Check
    Check --> Drop
    Check --> Send
```
`opted_out_notification_methods` 在 `Initialize` 握手期间填充。匹配为精确匹配（不支持通配符或前缀匹配）。

**常见退订模式**

-   退订 `item/agentMessage/delta`，以减少流式文本带宽
-   若只需最终状态，退订 `item/commandExecution/outputDelta`
-   使用 V2 API 时退订遗留事件

## 错误处理与韧性

转换层包含错误处理机制，确保事件处理中的失败不会导致整个线程崩溃。

**错误恢复模式**

| 错误场景 | 恢复策略 | 影响 |
| --- | --- | --- |
| 客户端在审批中途断开 | `oneshot::Receiver` 丢弃，核心超时 | 回合继续或干净失败 |
| 序列化失败 | 记录错误并跳过通知 | 事件丢失，但线程继续 |
| 转换逻辑 panic | 通过 `tokio::spawn` 任务隔离 | 单个事件丢失，其余继续 |
| 审批响应超时 | 核心收不到响应，应用默认处理 | 回合按拒绝继续 |

**审批响应处理**

```mermaid
flowchart TD
    SendRequest["send_request()returns oneshot::Receiver"]
    SpawnTask["tokio::spawn(async move { ... })"]
    AwaitResponse["rx.await"]
    Success["Result::OkMap to ReviewDecision"]
    Error["Result::ErrLog error"]
    ChannelClosed["oneshot::Receiver dropped"]
    SubmitOp["conversation.submit(Op)"]
    NoSubmit["No submit(core will timeout)"]

    SendRequest --> SpawnTask
    SpawnTask --> AwaitResponse
    AwaitResponse --> Success
    AwaitResponse --> Error
    AwaitResponse --> ChannelClosed
    Success --> SubmitOp
    Error --> NoSubmit
    ChannelClosed --> NoSubmit
```
