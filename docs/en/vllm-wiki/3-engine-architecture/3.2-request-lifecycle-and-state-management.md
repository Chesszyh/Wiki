This document describes how requests flow through vLLM's V1 engine, the states they transition through, and how their progress is tracked. It covers the `Request` object lifecycle from creation to completion, state transitions managed by the scheduler, and the mechanisms for tracking request progress and outputs.

## Purpose and Scope

This page documents:

-   The `Request` class and its role in tracking request state.
-   Request status states and state transition logic.
-   Request lifecycle from submission through completion.
-   How the scheduler manages request queues and state.
-   Request metadata tracking (tokens computed, outputs generated, etc.).
-   Special request states (preemption, streaming, remote KV loading).

### Status Descriptions

-   **`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`**: A request with structured output (JSON/Regex) waiting for the Finite State Machine/Grammar to be compiled [vllm/v1/request.py105](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/request.py#L105-L105)
-   **`WAITING_FOR_REMOTE_KVS`**: Request waiting for remote KV cache transfer in disaggregated prefill/decode scenarios [vllm/v1/core/sched/scheduler.py756](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L756-L756)
-   **`PREEMPTED`**: Request was previously `RUNNING` but was stopped to free GPU memory [vllm/v1/core/sched/scheduler.py307](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L307-L307)

## Scheduler State Management

### Request Queues

The `Scheduler` manages three primary collections of requests:

1.  **`self.requests`**: A dictionary mapping `request_id` to `Request` objects for all active requests [vllm/v1/core/sched/scheduler.py157](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L157-L157)
2.  **`self.waiting`**: A `RequestQueue` containing requests waiting to be scheduled [vllm/v1/core/sched/scheduler.py166](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L166-L166)
3.  **`self.running`**: A list of requests currently being processed [vllm/v1/core/sched/scheduler.py168](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L168-L168)

### Scheduling Cycle (`schedule()`)

The `schedule()` function is the core of state management:

-   It attempts to schedule new requests from the `waiting` queue based on the `SchedulingPolicy` (e.g., FCFS) [vllm/v1/core/sched/scheduler.py160](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L160-L160)
-   It checks resource constraints like `max_num_running_reqs` and `max_num_scheduled_tokens` [vllm/v1/core/sched/scheduler.py105-110](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L105-L110)
-   For each request, it interacts with the `KVCacheManager` to allocate blocks [vllm/v1/core/kv\_cache\_manager.py106](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/kv_cache_manager.py#L106-L106)

**Sources:** [vllm/v1/core/sched/scheduler.py322-897](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L322-L897) [vllm/v1/core/kv\_cache\_manager.py106-145](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/kv_cache_manager.py#L106-L145)

### Output Processing and Completion (`update_from_output()`)

After the `GPUModelRunner` executes, the scheduler updates request states:

-   **Token Update**: Increments `num_computed_tokens` and appends new `sampled_token_ids` [vllm/v1/core/sched/scheduler.py900-950](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L900-L950)
-   **Stop Condition**: Calls `check_stop()` to evaluate EOS tokens, stop strings, or max length [vllm/v1/core/sched/utils.py53](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/utils.py#L53-L53)
-   **Finished Requests**: If finished, the request is removed from `self.requests` and its KV blocks are freed via `finish_requests()` [vllm/v1/core/sched/scheduler.py294-320](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L294-L320)

**Sources:** [vllm/v1/core/sched/scheduler.py899-1204](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/core/sched/scheduler.py#L899-L1204)

## Structured Output State

For requests requiring structured output (e.g., JSON), state management involves the `StructuredOutputManager`.

1.  **Initialization**: `grammar_init(request)` is called when a request is added [vllm/v1/structured\_output/\_\_init\_\_.py97](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/__init__.py#L97-L97)
2.  **Compilation**: The manager uses a backend (like `XgrammarBackend`) to compile the schema into a `StructuredOutputGrammar` [vllm/v1/structured\_output/\_\_init\_\_.py117-147](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/__init__.py#L117-L147)
3.  **Execution**: During sampling, the grammar advances via `accept_tokens()` to constrain the next token selection [vllm/v1/structured\_output/backend\_xgrammar.py148](https://github.com/vllm-project/vllm/blob/7cc302dd/vllm/v1/structured_output/backend_xgrammar.py#L148-L148)
