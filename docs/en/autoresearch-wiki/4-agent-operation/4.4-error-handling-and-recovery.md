# Error Handling and Recovery

Relevant source files

-   [program.md](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1)

## Purpose and Scope

This document describes how the autoresearch system detects, categorizes, and recovers from errors during autonomous experimentation. It covers timeout detection, crash diagnostic procedures, simple fix attempts, and the logging of failures in `results.tsv`.

The system is designed for complete autonomy, allowing the agent to handle common issues like Out-of-Memory (OOM) errors, syntax mistakes, or execution timeouts without human intervention.

---

## Error Categories

The autoresearch system encounters three primary error categories during autonomous operation:

| Error Type | Cause | Detection Method | Recovery Strategy |
| --- | --- | --- | --- |
| **Timeout** | Experiment exceeds 10-minute wall clock limit | Wall clock timer monitoring | Kill process, discard changes, log as crash |
| **Crash (OOM)** | GPU VRAM exhaustion | Non-zero exit code | Discard changes, log as crash, try different approach |
| **Crash (Code Error)** | Syntax errors, runtime exceptions, missing imports | Non-zero exit code | Fix if trivial, otherwise discard and log as crash |

The system distinguishes between **trivial fixable errors** (typos, missing imports) and **fundamental problems** (architectural issues, OOM from excessive model size) using agent judgment.

## Timeout Detection and Handling

### Expected Runtime

Each experiment has an expected total runtime of approximately **7 minutes**:

-   5 minutes: Fixed training budget ([program.md23](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L23-L23))
-   ~1-2 minutes: Startup, compilation, and data loading.
-   ~30 seconds: Final evaluation via `evaluate_bpb` in `prepare.py` [prepare.py321-334](https://github.com/karpathy/autoresearch/blob/e6d79c12/prepare.py#L321-L334)

### Timeout Threshold

If an experiment exceeds **10 minutes** total wall clock time, it is considered a timeout failure. This threshold accounts for normal variance in startup and `torch.compile` time while preventing runaway processes.

## Crash Detection and Diagnostics

### Exit Code Monitoring

The agent executes experiments using shell redirection to capture all output for later diagnosis:

```
uv run train.py > run.log 2>&1
```
After execution completes, the agent checks the shell exit code. If the code is non-zero, it initiates diagnostic procedures.

### Diagnostic Procedure

When a crash is detected, the agent follows these steps:

1.  **Log Inspection**: Run `tail -n 50 run.log` to read the Python stack trace [program.md101](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L101-L101)
2.  **Error Categorization**: Identify if the error is a "dumb and easy to fix" typo or a fundamental flaw [program.md110](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L110-L110)
3.  **Metric Verification**: Use `grep "^val_bpb:\|^peak_vram_mb:" run.log` to confirm no metrics were produced [program.md100-101](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L100-L101)

### Common Crash Causes

| Crash Type | Typical Error Message | Root Cause | Fixable? |
| --- | --- | --- | --- |
| **OOM (CUDA)** | `RuntimeError: CUDA out of memory` | Model too large for GPU VRAM | No - requires scaling down |
| **Syntax Error** | `SyntaxError: invalid syntax` | Typo in `train.py` modification | Yes - simple fix |
| **Import Error** | `ImportError: cannot import name` | Missing import in `train.py` | Yes - add import |
| **Shape Mismatch** | `RuntimeError: mat1 and mat2 shapes` | Tensor dimension error in model | Maybe - check logic |

## Logging Failed Experiments

### results.tsv Entry Format

Failed experiments are logged to `results.tsv` (tab-separated) with sentinel values to ensure the log remains parseable by analysis tools like `analysis.ipynb`.

| Field | Value for Crash | Reason |
| --- | --- | --- |
| `commit` | 7-char hash | Identifies the failed attempt |
| `val_bpb` | `0.000000` | Sentinel for failure [program.md75](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L75-L75) |
| `memory_gb` | `0.0` | Sentinel for failure [program.md76](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L76-L76) |
| `status` | `crash` | Categorizes the run [program.md77](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L77-L77) |
| `description` | Error text | Explains why it failed [program.md78](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L78-L78) |

## Git State Management for Recovery

### Commit-Before-Execution Pattern

The agent uses a **commit-before-execution** strategy to enable clean rollback. This ensures that even if a crash occurs, the state of the code that caused the crash is preserved in the Git history (until reset) and can be referenced in `results.tsv`.

1.  **Modify**: The agent hacks `train.py` [program.md97](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L97-L97)
2.  **Commit**: Changes are committed to the local branch [program.md98](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L98-L98)
3.  **Execute**: `uv run train.py` is launched [program.md99](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L99-L99)
4.  **Evaluate/Recover**: If the run is worse or crashes, the agent performs `git reset` to return to the last successful "frontier" commit [program.md104](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L104-L104)

### Branch History

The Git branch (e.g., `autoresearch/mar5`) maintains a **clean linear history** containing only successful improvements. Failed experiments (crashes or regressions) are logged in `results.tsv` but their code changes are purged from the Git branch via reset.

## Agent Autonomy and Resilience

### No Human Intervention

The agent is instructed to **never stop** the experiment loop [program.md112](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L112-L112) This implies:

-   **Self-Correction**: If a crash happens, the agent must diagnose it independently.
-   **Persistence**: If one idea fails (crash), the agent must "think harder" and try a different architectural change [program.md112](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L112-L112)
-   **Judgment**: The agent uses its own judgment to decide when a fix is too complex and the idea should be abandoned [program.md101](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L101-L101)

### Handling Stuck States

If the agent gets stuck (e.g., multiple consecutive crashes), it is permitted to rewind or try radical architectural changes to find a viable path forward [program.md106](https://github.com/karpathy/autoresearch/blob/e6d79c12/program.md?plain=1#L106-L106) The primary goal is to minimize `val_bpb` while staying within the constraints of the `train.py` environment.
